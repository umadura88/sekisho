1背景と課題

近年のネットワーク装置監視は、gNMI に代表されるストリーミングテレメトリ(モデル駆動テレメトリ)へと 向かっている。しかし多くの通信事業者では、これらに対応しないレガシーな装置が依然として稼働しており、 SNMP Trap ベースの監視が数多く残っている。装置負荷の制約からポーリング頻度を上げられない環境では、 Trap が実質的に唯一の監視信号となる。ところが、広く運用されている OSS のツールチェーンは Trap をテキスト行として扱うものが主流のまま長年更新されておらず、宣言的な状態管理・ 過去イベントへのバックテスト・ルールの git 管理といった現代的な開発体験を備えた Trap 監視基盤は見当たらない。

1.1課題: 状態を持たない Trap と、構造を捨てるパイプライン

Trap 監視の課題は 2 層に分けて捉える必要がある。

  1. 本質的な課題 — Trap は状態(state)を持たない。監視が答えたいのは 「今どこが障害中か」という状態だが、Trap は「linkDown が届いた」という一瞬の イベントでしかない。イベントから状態を再構築する仕組み(raise と clear の対応づけ)は、 Trap を使う限り誰かが必ず解かなければならない。これはプロトコルの性質であり、 どのツールを使っても消えない
  2. 偶有的な課題 — 既存パイプラインが構造を捨てるため、1 を解くことが困難になる。 状態の同一性(「どの装置のどのポートか」= 状態キー)は varbind のインスタンス添字と値にしか 入っていないのに、既存パイプラインは入口でまさにそれをテキストに溶かしてしまう(§1.1.2)。 構造を失った時点で、状態キーの抽出も raise/clear の対応づけも regex 頼みになる

つまり、解くべき本質は 1 であり、2 はその解決を妨げている障害である。sekisho は 2 を「PDU を構造のまま扱う」ことで取り除き(§1.1.1、§5.1)、1 を状態エンジン(§5.3)で 正面から解く。まず §1.1.1 で、Trap が実際に運んでいるデータの形を具体例で確認する。

1.1.1SNMP Trap と varbind — 実際に届いているもの

SNMPv2 の Trap PDU(Protocol Data Unit)は varbind(OID + 型 + 値)のリストである。 具体例として、装置 10.0.0.1 の 1000 番インターフェース(ifIndex = 1000)がダウンした ときに届く linkDown Trap の中身を見る。

読み解くポイントは 3 つある。

  1. 先頭 2 つの varbind は SNMPv2 標準で固定されている。sysUpTime.0(装置の稼働時間)と snmpTrapOID.0(この Trap が「何であるか」)。受信側は varbind[1] の値を見るだけで 「これは linkDown である」と機械的に判定できる
  2. 3 つ目以降の varbind は MIB が宣言している。IF-MIB の NOTIFICATION-TYPE 定義(図 3)が 「linkDown は ifIndex, ifAdminStatus, ifOperStatus を運ぶ」と宣言し、それぞれの値の型と列挙も MIB が定義している。つまり Trap にはスキーマが存在する
  3. varbind の OID は「どのオブジェクトか」と「どの個体か」に分解できる。 1.3.6.1.2.1.2.2.1.8.1000 は、オブジェクト ifOperStatus(…2.2.1.8)に インスタンス添字 .1000(1000 番のインターフェース)が付いたものである

整理すると、1 つの Trap は構造的に 3 種類の情報を運んでいる。

表 1Trap PDU が運ぶ 3 種類の情報
情報在り処例
種別(何が起きた)第 2 varbind snmpTrapOID.0 の値1.3.6.1.6.3.1.1.5.3 = IF-MIB::linkDown
個体(どこで起きた)各 varbind の OID 末尾のインスタンス添字 / 索引 varbind の値ifOperStatus.1000 の .1000
属性(どんな状態か)varbind の型付きの値ifOperStatus = INTEGER 2(MIB の列挙で down(2))

つまり Trap は本来、スキーマ付きの構造化イベントである。図 1 の例だけからでも 「種別 = linkDown、個体 = ifIndex 1000、属性 = ifOperStatus down(2)」が、正規表現を一切使わずに 機械的に取り出せる。

1.1.2根本課題: 既存パイプラインが PDU をテキストに平坦化する副作用

典型的な snmptrapd → 従来型監視サーバのパイプラインは、この構造化データを 入口で一度テキストに平坦化してしまう (snmptrapd の整形出力 → 連携スクリプト → テキストログの 1 行)。 図 1 の Trap は、平坦化されるとたとえば次の 1 行になる。

図 1 で分かれていた種別・個体・属性・型・列挙定義が、1 本の文字列に融けている。 この行に対する監視ルールは、たとえば次のような正規表現トリガーにならざるを得ない。

型・OID の木構造・インスタンス添字・列挙定義を失った代償として、以降のすべての処理が regex による文字列マッチを強いられる。これが根本課題であり、 現場で広く観測される以下の症状はすべてここから派生する。

  • トリガーはテキストへの正規表現マッチで書くしかない。式が読めず、テストもできない。 種別・個体・属性の区別が失われているため、条件の意図がコードから読み取れない
  • インスタンス添字が文字列に埋没するため、インターフェース単位・ボード単位の障害管理には LLD(ローレベルディスカバリ)の迂回が必要で、Trap 駆動と相性が悪い。 結果として網羅的なトリガー整備を諦めるのが合理的になってしまう
  • どの正規表現にもマッチしなかった Trap は fallback に流れて事実上消滅し、観測手段がない
  • 平坦化後のテキストしか残らないため、トリガーの追加・変更を過去データで検証できず、 メンテナンスが停滞する
設計原理 sekisho はこの逆を行く: PDU を構造のまま受信・保存・照合し、テキスト化は表示の最終段でのみ行う(§5.1)。 あわせて、判定は決定的ルール、LLM はルール作成の支援に限定、その接点を MCP にする。

2監視の概念モデル

本章では、この設計で使う概念を定義する。以降の議論はすべてこの 4 つの概念の区別の上に 成り立つため、それぞれの境界を最初に明確にしておく。

表 24 概念の定義
概念本質主語可変性生成者
Event観測の事実。「linkDown という Trap が 10:03:21 に届いた」装置不変(追記のみ)装置
Alarm事実の解釈。「この IF は 10:03:21 から障害中」リソース(状態キー)状態遷移するルールエンジン
Alert解釈への反応。「これを夜間当番に通知する」人・チームポリシー次第Alert 層
Incident人間の対応。担当・タイムライン・振り返り運用組織ワークフロー別システム

2.1概念間の関係

  • Event : Alarm = N : 0..1。複数の Event が 1 つの Alarm の遷移を駆動する (linkDown が raise し、linkUp が clear する)。Alarm を生まない Event (drop されたもの、unrouted に落ちたもの)も正当な存在であり、消えずに Event 層に残る。 なお 0..1 は現行スコープで意図的に選んだ制約である(1 つの Event は高々 1 つのルールにマッチし、 高々 1 つの Alarm に影響する)。装置再起動 Trap による一括 clear のような 1:N の解釈は将来拡張とし、 その際は対応関係を alarm lifecycle event 側に持たせる
  • すべての Event はルーティング結果(route_id / action / 影響した alarm_id)を刻印される。 これにより Alert → Alarm → 構成 Event → 生 PDU まで完全な来歴(lineage)を遡れる
  • Trap は「Event の一種」であって同義ではない。将来 ICMP 生存確認の状態変化や syslog を 追加する場合、それらは同じ Event 層の別ソース種別になる
  • Alarm の状態遷移そのものも派生イベント(alarm lifecycle event)として記録する。 イベントには ingress event(世界からの入力)と alarm lifecycle event(エンジンの出力) の 2 系統があり、名前空間を分けて管理する

2.2境界を守る 3 つのルール

  1. Alarm はエンジンだけが作り、Alert はポリシーだけが作る。Alert 層の操作 (silence 等)が Alarm の状態に影響を与えることはなく、逆方向の作用は存在しない
  2. メンテナンスウィンドウは Alert 層の機能である。メンテナンス中でも Alarm は正しく raise/clear されて記録に残り、抑止されるのは通知だけである。これを混ぜてしまうと、 「メンテナンス中に実は壊れていた」という事実を後から追跡できなくなる
  3. ack は Alarm 層、silence は Alert 層に属する。ack は「事実を認知した」という 注記(監査対象)であり、silence は「この条件は通知するな」という判断である。似ているが別物なので、 両者は別の API として提供する

3スコープ

3.1スコープ内(コアエンジン)

  • Trap 受信 — SNMPv1 / v2c / v3 に対応する。v1 は RFC 3584 の変換で v2 形式に 正規化し、agent-addr フィールドは装置同定(§5.1)に利用する。v3 は USM(認証・暗号化)に対応し、 資格情報の管理は §11 で扱う。INFORM(確認応答付き通知)は対象外。経路は当面 snmptrapd forward、 将来自前 162 受信
  • MIB 解決(ベンダ各社の private MIB。未解決 OID は生のまま通す寛容設計)
  • アラートルーティングテーブル(snmpTrapOID longest-prefix match + varbind 条件)
  • 状態エンジン(raise/clear ペアリング、flapping 検出、状態キー)= Alarm 管理
  • Event 全量保存と来歴刻印
  • alarm.* ストリーム出力(Webhook)+ ack API
  • MCP サーバ(unmatched 観測、ルール提案、バックテスト、適用)
  • LLM プロバイダ抽象(Bedrock / ローカル LLM)
  • REST API(状態エンジン・ルート・イベント検索・ack への唯一のアクセス面)と、その薄い クライアントとしての CLI(sekisho コマンド)・Web UI(ルートテーブル + カウンタ、 Active Alarm List、イベント検索)

3.2非スコープ

  • Alert 管理(silence、当番表、集約、エスカレーション)— alarm.* ストリームの購読者として 将来増設、または Alertmanager 等の既存品を接続
  • Incident 管理 — 別システムとして確定。接続点は alarm.* ストリームのみ。 コアのリポジトリ・プロセス・DB に Incident の概念を持ち込まない
  • メトリクスポーリング、gNMI。汎用のイベントソースプラグイン機構も v1 では作らない — ソースは内蔵実装とし、概念上の拡張点(§2.1)だけを予約する

4アーキテクチャ

設計原則 判定エンジンのホットパスでは LLM を一切呼ばない。判定は常に決定的であり、同じ入力からは必ず同じ結果が再現される。

外部インターフェースは API ファーストで統一する。Alarm・ルート・イベント検索・ack を 含む状態エンジンへのアクセスはすべて REST API として公開し、Web UI・CLI (sekisho コマンド。sekisho route show 等)・MCP サーバは、いずれも同じ API の 薄いクライアントとして実装する。これにより認証・認可・監査・互換性の管理点が API の 1 箇所に集約される。 Web UI は React 等のモダンな SPA として実装し、ビルド済みアセットを sekisho バイナリに埋め込んで 配信する(単一バイナリ配布と起動の簡単さを保ったまま、エンジン・データへのフル機能アクセスを提供する)。 push 型の契約である alarm.* ストリーム(§7)だけは、この API と並ぶもう 1 つの外部面である。

5マッチングモデルとアラートルーティングテーブル

5.1Trap の解剖学 — 3 つの情報の役割分担

sekisho は、§1.1.1 で見た 3 種類の情報を次のように使い分ける。この 3 役を混ぜないことが、マッチング設計の核心である。

表 43 役と sekisho での用途
#情報sekisho での役割
1種別(snmpTrapOID)ルーティングの match 対象(longest-prefix)
2個体(インスタンス添字 / 索引 varbind)状態キーの抽出元。マッチには使わない
3属性(型付きの値)条件(where)と遷移判定

「varbind 照合 = 文字列マッチ」になるのは SNMP の性質ではなく、既存パイプラインの平坦化の アーティファクトである(§1.1.2)。sekisho は PDU を構造のまま保持し、MIB の型情報で照合する。

この前提から導かれるマッチング原則:

  1. varbind は位置ではなく OID で特定する。MIB の NOTIFICATION-TYPE 定義(OBJECTS 句)が 「この Trap はどの varbind を運ぶか」を宣言しているが、ベンダ実装は varbind を追加してくる ことがあるため、順序に依存しない
  2. 値の照合はシンボリックに書き、型付きにコンパイルする。ルールに ifOperStatus: down と 書けば、エンジンが MIB の列挙定義から (base OID 1.3.6.1.2.1.2.2.1.8, INTEGER 2) に解決して 比較する。regex は登場しない
  3. インスタンス添字は分解して取り出す。受信時に各 varbind を (base OID, instance suffix, typed value) に分解する。状態キーは索引 varbind の値 ({ifIndex})からも、添字({instance_of(ifOperStatus)})からも取れる
  4. MIB が欠けた varbind は生 OID + 生値のまま通し、生値での照合も許す(縮退動作)

また、状態キーの素材となる装置の同定(device identity)を受信処理の第一級ステージとして 扱う。装置は (a) パケットの送信元 IP、(b) v1→v2 変換時に付与される snmpTrapAddress.0 varbind、(c) varbind 内の装置識別子(sysName 等)、(d) インベントリによるマッピング、の優先順で device_id に解決される。ルール中の {source} は生の送信元 IP ではなく、 この解決済み device_id を指す(受信方式との適合性は §10.1)。なお ifIndex は装置再起動や カード交換で振り直され得るため、状態キーの素材には ifName 等の安定した識別子の併用を検討する。

5.2ルーティングテーブル

トリガーではなく「ルートテーブル + ポリシー」として監視ルール全体を設計する。 match の対象は snmpTrapOID(種別)であり、その値は enterprise 配下の木構造を成すため longest-prefix match がそのまま成立する。varbind 条件(where)は PBR に相当する。

  • specific 勝ち(longest-prefix match)、default 経由、drop という ネットワークエンジニアの語彙・メンタルモデルをそのまま使う
  • 全ルートにヒットカウンタと最終ヒット時刻を持つ(描画は図 9)。 drop ルートにもカウンタを付け、「何を黙って捨てているか」を常時可視化する
  • unrouted は Trap が消えていく先ではなく、それ自体が観測対象である。ここからルール提案(§8)が生まれる。 なお「バケット」は独立した保存先ではない。Event は全量が ClickHouse に入るため、unrouted とは route_id = '' が刻印された Event の論理ビューであり、頻度集計は Materialized View で常時維持される(保持期間も他の Event と同一)
  • ルートとルールはただの YAML ファイルで git 管理。レビュー・差分・ロールバックは 通常の開発フローに乗る
  • マッチングは全順序を持ち、決定的である。ルートは prefix 長 → 定義ファイル内の順序で 評価され、trap_oid と where の両方が成立した最初のルートが選ばれる。 重複・曖昧なルートや、MIB で解決できないシンボルを参照するルールは、ロード時に検出して エラーまたは警告付き無効化とする

ルートテーブルは、ネットワーク OS の show route と同じ思想で描画可能で なければならない。正はあくまで YAML の設定ファイルだが、運用者が見るのは常に「評価順に並び、 カウンタを伴う 1 枚の表」である。CLI(sekisho route show)と Web UI は同じ描画を返す。

5.3stateful ルール — raise/clear の 3 パターン

現実の装置が raise/clear を表現する方法は 3 パターンに大別され、DSL はそのすべてを直接表現できる。

パターン A: 種別ペア型 — raise と clear が別々の Trap(linkDown / linkUp)。

パターン B: 状態 varbind 型 — 単一の Trap 種別で、varbind の値が raise/clear を決める。 汎用アラーム通知を 1 本の Trap で表現する装置に多い。

パターン C: アラーム ID 照合型 — X.733 系の設計で、raise 通知と clear 通知が 共通のアラーム識別子 varbind で対応づく。キーにその識別子を使うことでパターン A/B に還元される (key: "{source}:{alarmSeq}")。

いずれのパターンでも、設計上の要点は共通している。

  1. raise/clear の対応を 1 つのルールに書く(トリガー 2 分裂・障害復旧式の分離をしない)
  2. 状態キーを宣言する。キーの材料は種別(役割 1)ではなく個体(役割 2)から取る
  3. 遷移条件は型付き値(役割 3)で書く。文字列 regex はどこにも登場しない
  4. flapping の扱いはルール内で宣言的に定義する(時間窓と回数を指定し、閾値を超えたら Alarm を flapping 状態に遷移させる)

raise/clear モデルには clear の消失に対する縮退方針が必須である。Trap は UDP で 失われ得るため(§12)、clear を取りこぼした Alarm は放置すれば永久に残り、Active Alarm List の 信頼性を損なう。sekisho は次の 3 つを仕様として持つ。

  1. 失効ポリシー: ルール単位で expire_after(例: 7d)を宣言でき、 期限を超えた Alarm は理由 expired 付きで自動 clear される
  2. 手動 clear API: 運用者による強制 clear を監査付きで提供する。装置由来の clear とは 理由コード(trap / manual / expired)で区別され、alarm lifecycle event に記録される
  3. 対応する raise の無い clear: イベントとして記録した上で、状態遷移は起こさない

flapping は通知の抑制ではなく、Alarm の明示的な状態として扱う(§2.2 の境界ルールとの 整合)。時間窓内の遷移回数が閾値を超えると Alarm は flapping 状態に入るが、個々の遷移はイベントとして 記録され続ける。静穏期間(calm、例: 15 分無遷移)で flapping は解除され、開始と終了は alarm.flapping / alarm.updated で上位層に通知される。通知のダンピング自体は Alert 層の責務である。Alarm のタイムラインは受信時刻(received_at)を正とし、 近接した順序逆転(linkUp が linkDown より先に届く等)の扱いは猶予窓として LLD で定義する。

7alarm.* ストリーム(上位層との契約)

alarm.* ストリームは、将来の Alert 層や Incident 管理システムとの唯一の接続点である。 この契約が安定していることが、レイヤ分離を成立させる前提となる。

  • イベント種別: alarm.raised / alarm.updated / alarm.flapping / alarm.cleared / alarm.acked。alarm.updated は severity または 注記属性が変化したときにのみ発火し、同一状態の再観測(重複 raise)では発火しない(回数は Alarm 側の カウンタに反映される)。alarm.cleared は理由コード(trap / manual / expired)を持つ
  • ペイロード: 安定した alarm_id、alarm_id ごとに単調増加するシーケンス番号、 状態キー、severity、rule/route の識別子、遷移を起こした ingress event の event_id(lineage)
  • 配送: 当面 Webhook。at-least-once であり、順序は alarm_id 単位の直列配送で保証する。 購読者は (alarm_id, seq) による重複排除を実装することを契約とする。配送失敗は 指数バックオフで再試行し、長時間滞留した場合の復旧は list_alarms による全量リコンサイルを推奨する
  • 配送先(sink)はプラグイン可能な抽象とする。標準実装は Webhook と カスタムスクリプト実行(alarm.* の JSON を標準入力で渡して任意のスクリプトを起動する)の 2 つで、特定の連携先を仮定しない疎結合を優先する。スクリプト実行は outbox の先の配送ワーカーに 隔離されており、受信ホットパス(§12)には影響しない
  • スキーマはバージョン付き JSON とし、後方互換を守る(互換性ポリシーは §14)

10.1受信経路の選択肢と移行計画

最終形は、sekisho が 162 番ポートで Trap を直接受信する構成である。ただし直接受信への切り替えは 装置側の Trap 宛先変更を伴うため、移行期には既存環境にほぼ手を入れずに Trap の複製を得る手段が 必要になる。選択肢は 3 つある。

方式の選択は状態エンジンと連動する。forward 方式は送信元 IP を失うため、§5.1 の device_id 解決が varbind 経由(snmpTrapAddress.0 や装置識別子)で成立する場合にのみ、状態エンジンの 前提を満たす。成立しない環境では、forward での並走は M1(構造化蓄積と unrouted の観測)までの 検証と位置づけ、状態エンジン(M2)はパケット複製以降で有効化する。

複製されたパケットは送信元 IP・ポートを保ったまま届くため、sekisho は装置を送信元 IP で同定できる。 注意点は 2 つある。第一に、複製はカーネルによる一方向のクローンであり応答経路を持たないが、 Trap はもともと応答を要求しないため問題にならない。第二に、宛先ポートは 162 のまま複製されるため、 sekisho は snmptrapd とは別のホスト(または独自の IP を持つコンテナ)で 162 番を listen する 必要がある。加えて dup/TEE は宛先 IP を書き換えない複製であるため、sekisho ホスト側での DNAT(図 14 の 3 ブロック目)が必須であり、実質 L2 隣接を前提とする。経路上のファイアウォールや アンチスプーフィング機構で複製パケットが落ちないことも導入前の検証項目である。

推奨する移行順序は次のとおりである。Phase 1a: forward で最小の手数で並走を開始する。 送信元 IP が必要になった時点で Phase 1b: パケット複製へ切り替える。最終的に Phase 2: 装置側の宛先変更を伴う直接受信へ移行し、snmptrapd を退役させる。

移行期の運用として、次の 3 点を §12 の自己監視とあわせて計画する。並走検証 — 既存ツールの障害一覧と sekisho の Active Alarm List を一定期間突き合わせ、一致率を移行判断の基準に する。重複受信の方針 — 方式の併用期間には同一 Trap を二重受信し得るが、同一キーへの 再 raise は状態遷移を起こさない(通知も増えない)。切り戻し — 各 Phase は独立に 無効化でき、既存側は常に無変更で残るため、戻し先が失われることはない。

11セキュリティモデル

監視システムは、攻撃者にとって「目を潰す」対象である。信頼境界と権限は設計段階で確定させる。

  • ルール変更の唯一のゲートは git である。apply_rule を含むどの経路も エンジンのルールを直接書き換えることはできず、MCP からの適用は Pull Request の作成までとする。 エンジンは保護ブランチからのみルールをロードするため、人間によるマージが承認の強制点となる (「人間の承認」を運用ルールではなく仕組みとして担保する)
  • MCP ツールは read-only と write に分離する。観測系(list_* / sample_* / get_* / backtest_rule)と変更系(propose_rule / apply_rule)で権限を分け、 認証・認可は MCP 接続単位で行う
  • LLM へのデータ送信は方針として制御する。propose_rule が外部 LLM (Bedrock)へ送るのは MIB 定義と varbind サンプルであり、装置 IP 等の識別子はマスキングできる。 外部送信を許容しない環境向けに、ローカル LLM 限定モードを提供する
  • Webhook は署名する(HMAC)。購読者は署名検証によって偽の alarm.* を排除できる
  • 162 番直接受信(Phase 2)では受信 ACL とコミュニティ検証を必須とする。UDP は 送信元を偽装できるため、送信元アドレスの許可リストを一次防御とする。SNMPv3 の USM(認証・暗号化)に 対応し、ACL と併用してスプーフィング耐性を高める。資格情報(engineID・ユーザ・鍵)は設定として 管理し、平文では保存しない

12信頼性設計

Caution Trap は UDP で再送がないため、届かないことがある。そのため Trap だけに頼る監視は 「無音」と「正常」を区別できない。対策として、ICMP ping 程度の超軽量な生存確認を将来の イベントソースとして併設する(装置負荷は実質ゼロで済む)。これは Event 層の別ソース種別として §2.1 の拡張点に位置づけられる。
  • MIB は必ず欠けるものとして設計する。未解決 OID の Trap も落とさず、生のまま Event 層に通す(§5.1 の縮退動作)
  • flapping や Trap ストームの際に、受信経路では fork や外部プロセスの起動を行わない。 これが snmptrapd の traphandle を使わない理由である。外部プロセスを起動するのは alarm.* 配送の スクリプト sink(§7)だけであり、outbox の先の配送ワーカーに隔離されている
  • ストーム時の縮退: 受信から格納までは有界キューで接続し、ClickHouse 停止時は ローカルディスクのスプール(WAL)で受信を継続する。それでも溢れた場合の drop は必ず自己カウンタに 計上し、「黙って捨てる」ことはしない。ストーム時には MIB 解決などの派生処理を後回しにする 縮退モードを持つ
  • 自己監視: 受信レート、キュー深度、drop 数、unrouted 率、ストア書き込み遅延、 Webhook 配送失敗、最終 Trap 受信時刻を、標準のメトリクスエンドポイント(Prometheus 形式)で公開する。 sekisho 自身の沈黙は、外部の watchdog が heartbeat で検知する前提とする
  • 目標負荷: 定常 500 traps/sec を drop なしで処理する。ストーム時はその 10 倍 (5,000 traps/sec)の短時間バーストを有界キューとスプールで吸収する。この域は単一 Go プロセスで 十分に達成可能であり、次項の単一インスタンス前提の根拠でもある
  • 可用性の非目標: v1 は単一インスタンスを前提とし、HA は非目標として明示する。 将来の水平分割は、状態キーが装置を含むことから device_id ハッシュが自然な分割軸になる
  • INFORM(確認応答付き通知)には対応しない。UDP 消失への備えは、失効ポリシー(§5.3)・ ping 生存確認(将来ソース)・本節の自己監視の組み合わせで行う

1Background and Problem

Network device monitoring has been moving toward streaming (model-driven) telemetry, exemplified by gNMI. Many network operators, however, still run legacy devices that do not support these interfaces, and SNMP trap-based monitoring remains widespread. In environments where polling frequency cannot be raised due to device load constraints, traps are effectively the only monitoring signal. Yet the widely deployed OSS toolchains still treat traps as text lines and have gone without meaningful updates for years; a trap monitoring platform with a modern development experience — declarative state management, backtesting against historical events, rules under git — is nowhere to be found.

1.1Problem: stateless traps, and pipelines that discard structure

The problem with trap-based monitoring must be understood as two distinct layers.

  1. The essential problem — traps carry no state. Monitoring wants to answer "what is broken right now", which is a state; a trap is only a momentary event ("a linkDown arrived"). Reconstructing state from events — pairing raises with clears — is something every trap consumer must solve. It is a property of the protocol, and no tool makes it disappear
  2. The accidental problem — existing pipelines throw the structure away, which makes problem 1 hard to solve. State identity ("which port on which device" — the state key) lives only in the varbind instance suffixes and values, yet existing pipelines melt exactly that into text at the entrance (§1.1.2). Once the structure is gone, both key extraction and raise/clear pairing degenerate into regex work

In short, problem 1 is the real target, and problem 2 is the obstacle in front of it. sekisho removes problem 2 by keeping the PDU structured (§1.1.1, §5.1), and solves problem 1 head-on with the state engine (§5.3). §1.1.1 first shows, with a concrete example, what a trap actually carries.

1.1.1SNMP traps and varbinds — what actually arrives

An SNMPv2 trap PDU (Protocol Data Unit) is a list of varbinds (OID + type + value). As a concrete example, here is the linkDown trap that arrives when interface 1000 (ifIndex = 1000) on device 10.0.0.1 goes down.

Three things are worth reading out of this.

  1. The first two varbinds are fixed by the SNMPv2 standard: sysUpTime.0 (device uptime) and snmpTrapOID.0 (what this trap is). A receiver can determine "this is a linkDown" mechanically by looking at varbind[1] alone
  2. The remaining varbinds are declared by the MIB. The IF-MIB NOTIFICATION-TYPE definition (Figure 3) declares that linkDown carries ifIndex, ifAdminStatus, and ifOperStatus, and the MIB also defines each value's type and enum. In other words, traps have a schema
  3. A varbind's OID decomposes into "which object" and "which instance": 1.3.6.1.2.1.2.2.1.8.1000 is the object ifOperStatus (…2.2.1.8) with the instance suffix .1000 (interface number 1000) appended

In summary, a single trap structurally carries three kinds of information.

  • Triggers can only be written as regular expressions over text. The expressions are hard to read and impossible to test. Because the kind/instance/attribute distinction has been lost, the intent of a condition cannot be recovered from the code
  • Instance suffixes are buried inside strings, so per-interface or per-board fault management requires a detour through low-level discovery (LLD), which fits trap-driven monitoring poorly. Giving up on comprehensive trigger coverage becomes the rational choice
  • Traps that match no regex fall into a fallback and effectively vanish, with no way to observe them
  • Since only the flattened text remains, trigger additions and changes cannot be validated against historical data, and maintenance stalls
Design principle sekisho takes the opposite approach: receive, store, and match the PDU in its structured form; render to text only at the final display stage (§5.1). In addition: all decisions are made by deterministic rules; LLMs are limited to assisting rule authoring; and the interface between the two is MCP.

2.1Relations between concepts

  • Event : Alarm = N : 0..1. Multiple events drive the transitions of a single alarm (a linkDown raises it, a linkUp clears it). Events that produce no alarm — dropped ones, unrouted ones — are equally legitimate and remain in the event layer. The 0..1 is a constraint chosen deliberately for the current scope (one event matches at most one rule and affects at most one alarm); 1:N interpretations, such as a device-reboot trap bulk-clearing many alarms, are a future extension, at which point the mapping will live on the alarm lifecycle events
  • Every event is stamped with its routing outcome (route_id / action / affected alarm_id). This gives complete lineage: from an alert back through the alarm and its contributing events all the way to the raw PDU
  • A trap is one kind of event, not a synonym. Future sources — ICMP liveness state changes, syslog — enter the same event layer as additional source types
  • Alarm state transitions are themselves recorded as derived events (alarm lifecycle events). There are thus two families of events with separate namespaces: ingress events (input from the world) and alarm lifecycle events (output of the engine)

2.2Three boundary rules

  1. Only the engine creates alarms; only policy creates alerts. No backflow: alert-layer operations (silences etc.) never affect alarm state
  2. Maintenance windows are an alert-layer feature. During maintenance, alarms are still raised and cleared correctly and remain on record; only notification is suppressed. Mixing the two makes "it was actually broken during the maintenance window" impossible to trace afterwards
  3. ack belongs to the alarm layer, silence to the alert layer. An ack is an audited annotation on a fact ("we are aware of this"); a silence is a decision ("do not notify on this condition"). They get separate APIs

3Scope

3.1In scope (the core engine)

  • Trap reception — SNMPv1 / v2c / v3. v1 traps are normalized to v2 form per RFC 3584, with the agent-addr field feeding device identity resolution (§5.1); v3 supports USM (authentication and privacy), with credential management covered in §11. INFORMs (acknowledged notifications) are out of scope. Via snmptrapd forward initially; native listener on port 162 later
  • MIB resolution (vendor private MIBs; unresolved OIDs pass through raw — tolerant by design)
  • The alert routing table (longest-prefix match on snmpTrapOID + varbind conditions)
  • The state engine (raise/clear pairing, flap detection, state keys) = alarm management
  • Full event retention with routing-outcome lineage
  • alarm.* stream output (webhooks) + ack API
  • MCP server (unmatched-trap observability, rule proposals, backtests, apply)
  • LLM provider abstraction (Bedrock / local LLM)
  • A REST API (the single access surface for the state engine, routes, event search, and ack), with a thin CLI (the sekisho command) and a Web UI (route table + counters, active alarm list, event search) as its clients

3.2Out of scope

  • Alert management (silences, on-call rosters, dedup/grouping, escalation) — added later as a subscriber of the alarm.* stream, or delegated to existing tools such as Alertmanager
  • Incident management — a separate system by decision. The only connection point is the alarm.* stream. No incident concepts enter the core's repository, process, or database
  • Metric polling and gNMI. Nor is there a generic event-source plugin mechanism in v1 — sources are built-in implementations; only the conceptual extension point (§2.1) is reserved

4Architecture

Design principle The decision engine's hot path never calls an LLM. Deterministic and reproducible.

External interfaces are unified API-first. All access to the state engine — alarms, routes, event search, ack — is exposed as a REST API, and the Web UI, the CLI (the sekisho command, e.g. sekisho route show), and the MCP server are all implemented as thin clients of that same API. Authentication, authorization, auditing, and compatibility are thereby managed at a single point. The Web UI is a modern SPA (React), with its built assets embedded in the sekisho binary — full access to the engine and its data without giving up single-binary distribution and trivial startup. The alarm.* stream (§7), being a push contract, is the one other external surface alongside the API.

5Matching Model and the Alert Routing Table

5.1Anatomy of a trap — three roles, kept separate

sekisho assigns the three roles of §1.1.1 as follows. Keeping them separate is the core of the matching design.

Table 4The three roles and their use in sekisho
#InformationRole in sekisho
1Kind (snmpTrapOID)What routing matches on (longest-prefix)
2Instance (instance suffix / index varbind)Source of the state key; never used for matching
3Attributes (typed values)Conditions (where) and transition decisions

"Varbind matching = string matching" is not a property of SNMP; it is an artifact of the flattening in existing pipelines (§1.1.2). sekisho keeps the PDU structured and matches using the MIB's type information.

Matching principles that follow from this premise:

  1. Identify varbinds by OID, not by position. The MIB's NOTIFICATION-TYPE definition (OBJECTS clause) declares which varbinds a trap carries, but vendor implementations sometimes append extra varbinds, so ordering is never relied upon
  2. Write comparisons symbolically; compile them to typed values. A rule that says ifOperStatus: down is resolved by the engine through the MIB enum into (base OID 1.3.6.1.2.1.2.2.1.8, INTEGER 2) for comparison. No regex anywhere
  3. Decompose instance suffixes on receipt. Each varbind is split into (base OID, instance suffix, typed value). State keys can be built from index varbind values ({ifIndex}) or from suffixes ({instance_of(ifOperStatus)})
  4. Varbinds whose MIB is missing pass through as raw OID + raw value, and raw-value matching is allowed (graceful degradation)

Device identity resolution — the material for state keys — is a first-class stage of reception. A device resolves to a device_id in this order: (a) the packet's source IP, (b) the snmpTrapAddress.0 varbind added by v1→v2 conversion, (c) device identifiers carried in varbinds (e.g. sysName), (d) an inventory mapping. {source} in rules refers to this resolved device_id, not the raw source IP (see §10.1 for how this interacts with the reception method). Note that ifIndex may be renumbered by reboots or card swaps, so stable identifiers such as ifName should be considered as key material.

5.2Routing table

The entire rule set is designed as a route table with policies, not as triggers. Matching targets the snmpTrapOID (the kind), whose values form a tree under each enterprise arc — so longest-prefix matching applies directly. Varbind conditions (where) are the analogue of policy-based routing.

  • Reuses the network engineer's vocabulary and mental model as-is: most-specific wins (longest-prefix match), via default, and drop
  • Every route carries a hit counter and a last-hit timestamp (rendered as in Figure 9). Drop routes get counters too, keeping "what we are silently discarding" visible at all times
  • The unrouted bucket is not where traps go to die — it is itself an object of observation, and the source of rule proposals (§8). The "bucket" is not a separate store: every event lands in ClickHouse, so unrouted is a logical view over events stamped with route_id = '', with frequency aggregates maintained by a materialized view (and the same retention as every other event)
  • Routes and rules are plain YAML files under git: review, diff, and rollback ride the normal development workflow
  • Matching is totally ordered and deterministic. Routes are evaluated by prefix length, then by order within the definition file; the first route whose trap_oid and where both hold is selected. Duplicate or ambiguous routes, and rules referencing symbols the MIB cannot resolve, are detected at load time and rejected or disabled with a warning

The route table must be renderable in the same spirit as a network OS's show route. The YAML files remain the source of truth, but what an operator looks at is always a single table in evaluation order, with counters. The CLI (sekisho route show) and the Web UI return the same rendering.

5.3Stateful rules — the three raise/clear patterns

Real devices express raise/clear in three broad patterns, and the DSL expresses all of them directly.

Pattern A: paired kinds — raise and clear are distinct traps (linkDown / linkUp).

Pattern B: status varbind — a single trap kind whose varbind value decides raise/clear. Common on devices that express generic alarm notifications through one trap.

Pattern C: alarm-ID correlation — X.733-style designs where the raise and clear notifications share a common alarm-identifier varbind. Using that identifier as the key (key: "{source}:{alarmSeq}") reduces this to patterns A/B.

In every pattern, the design points are the same:

  1. The raise/clear pair is written in one rule (no splitting into two triggers, no separate recovery expression)
  2. The state key is declared. Its material comes from the instance (role 2), never from the kind (role 1)
  3. Transition conditions are written over typed values (role 3). String regexes appear nowhere
  4. Flapping is declared inside the rule (a time window and count; past the threshold, the alarm transitions into the flapping state)

The raise/clear model requires a degradation policy for lost clears. Traps can be lost in transit (§12); an alarm whose clear was missed would otherwise stay raised forever and erode the trustworthiness of the active alarm list. sekisho specifies three mechanisms.

  1. Expiry policy: a rule may declare expire_after (e.g. 7d); alarms past the deadline are auto-cleared with reason expired
  2. Manual clear API: operators can force-clear with an audit trail. It is distinguished from device-originated clears by a reason code (trap / manual / expired) recorded on the alarm lifecycle event
  3. Clears with no matching raise are recorded as events but cause no state transition

Flapping is treated not as notification suppression but as an explicit alarm state (consistent with the boundary rules of §2.2). When transitions within the window exceed the threshold, the alarm enters the flapping state — while every individual transition continues to be recorded as an event. A calm period (calm, e.g. 15 minutes without transitions) ends the flapping state; start and end are announced via alarm.flapping / alarm.updated. Notification damping itself remains the alert layer's responsibility. Alarm timelines are authoritative on received_at; handling of closely spaced out-of-order arrivals (a linkUp arriving before its linkDown) is defined in the LLD as a grace window.

7The alarm.* Stream (the contract with upper layers)

The single connection point to the future alert layer and incident systems. Its stability is the lifeline of the layer separation.

  • Event kinds: alarm.raised / alarm.updated / alarm.flapping / alarm.cleared / alarm.acked. alarm.updated fires only when severity or annotation attributes change — never on re-observation of the same state (duplicate raises increment a counter on the alarm instead). alarm.cleared carries a reason code (trap / manual / expired)
  • Payload: a stable alarm_id, a monotonically increasing sequence number per alarm_id, the state key, severity, rule/route identifiers, and the event_id of the ingress event that drove the transition (lineage)
  • Delivery: webhooks initially. At-least-once, with ordering guaranteed by serialized delivery per alarm_id. Subscribers must deduplicate on (alarm_id, seq) — this is part of the contract. Failed deliveries retry with exponential backoff; after prolonged backlog, full reconciliation via list_alarms is the recommended recovery
  • Sinks are a pluggable abstraction. The two standard implementations are webhooks and custom script execution (any script invoked with the alarm.* JSON on stdin), favoring loose coupling over assumptions about the receiving system. Script execution runs in the delivery workers beyond the outbox, isolated from the reception hot path (§12)
  • The schema is versioned JSON with backward compatibility maintained (compatibility policy in §14)

8.1The rules repository and CI/CD (GitHub integration)

Route and rule YAML lives in a repository separate from the sekisho codebase. The software's release cycle and the monitoring rules' change cycle are independent, and so is ownership (the rules repository belongs to the operations team).

  • Template generation: sekisho rules init scaffolds the rules repository — directory conventions, sample rules, and a complete CI workflow (GitHub Actions) — so PR-driven operation works from the moment the repository is created
  • CI: every PR runs sekisho rules lint (syntax, MIB resolution, duplicate-route checks) and a backtest via the REST API; the impact — "1,243 matches over the past 30 days, 37 alarms generated" — is posted automatically as a PR comment. Reviewers see the diff and its impact on the same screen
  • CD: the engine watches only the protected branch (webhook or polling), validates merged commits, and loads them. Load outcomes (success / warning / rejection) are recorded in the self-monitoring metrics (§12)
  • apply_rule is implemented as opening a PR against this repository — one mechanism with the gate of §11

10.1Reception options and the migration plan

The end state is sekisho listening for traps directly on port 162. Since switching to direct reception requires changing the trap destination on the devices, the transition period needs a way to obtain a copy of the traps with almost no changes to the existing environment. There are three options.

Table 7Three ways to obtain a copy of the traps during migration
MethodMechanismSource IPImpact on existing setup

The choice interacts with the state engine. Because forward loses the source IP, it satisfies the state engine's preconditions only where device identity resolves via varbinds (snmpTrapAddress.0 or device identifiers, §5.1). Where it does not, treat the forward-based phase as validation of M1 only (structured retention and unrouted observation), and enable the state engine (M2) from packet duplication onward.

Duplicated packets arrive with the source IP and port preserved, so sekisho can identify devices by source address. Two caveats: first, duplication is a one-way kernel clone with no return path — which is fine, because traps expect no response. Second, packets are cloned with the destination port still 162, so sekisho must listen on 162 on a separate host (or a container with its own IP), not alongside snmptrapd. In addition, dup/TEE clone packets without rewriting the destination IP, so the DNAT on the sekisho host (third block of Figure 14) is mandatory, and the setup effectively assumes L2 adjacency. Verifying that no firewall or anti-spoofing device on the path drops the cloned packets is a pre-deployment checklist item.

The recommended sequence is Phase 1a: start running alongside via forward with minimal effort; switch to Phase 1b: packet duplication once the source IP becomes necessary; and finally Phase 2: direct reception with the device-side destination change, retiring snmptrapd.

Three operational practices accompany the transition, planned together with the self-monitoring of §12. Parallel-run validation — reconcile the legacy tool's problem list against sekisho's active alarm list over a fixed period, and use the agreement rate as the migration criterion. Duplicate reception policy — while methods overlap, the same trap may arrive twice; a re-raise on the same key causes no state transition (and no extra notification). Rollback — each phase can be disabled independently, and the legacy side remains untouched throughout, so there is always a path back.

11Security Model

A monitoring system is, to an attacker, the thing you blind first. Trust boundaries and privileges are fixed at design time.

  • git is the single gate for rule changes. No path — including apply_rule — writes engine rules directly; applying via MCP goes only as far as opening a pull request. The engine loads rules exclusively from a protected branch, so a human merge is the enforced approval point ("human approval" is guaranteed by mechanism, not by convention)
  • MCP tools are split into read-only and write. Observation tools (list_* / sample_* / get_* / backtest_rule) and mutation tools (propose_rule / apply_rule) carry separate privileges; authentication and authorization are per MCP connection
  • Data sent to LLMs is governed by policy. What propose_rule sends to an external LLM (Bedrock) is MIB definitions and varbind samples; identifiers such as device IPs can be masked. A local-LLM-only mode is provided for environments that forbid external egress
  • Webhooks are signed (HMAC), so subscribers can reject forged alarm.* events
  • Direct reception on port 162 (Phase 2) requires a reception ACL and community validation. UDP sources can be spoofed; a source-address allowlist is the first line of defense. SNMPv3 USM (authentication and encryption) is supported and, combined with the ACL, hardens spoofing resistance. Credentials (engineID, users, keys) are managed as configuration and never stored in plaintext

12Reliability Design

Caution Traps are UDP with no retransmission and can fail to arrive. Pure trap monitoring cannot distinguish "silence = healthy". An ultra-lightweight liveness check on the order of ICMP ping will be added as a future event source (device load is effectively zero); it enters the event layer as another source type per §2.1.
  • MIBs are assumed to be incomplete. Traps with unresolved OIDs still flow through to the event layer in raw form (the graceful degradation of §5.1)
  • The reception path never forks or spawns external processes during flapping or trap storms (the reason snmptrapd's traphandle is not used). The only place external processes run is the alarm.* script sink (§7), isolated in the delivery workers beyond the outbox
  • Degradation under storms: reception and storage are connected by bounded queues; while ClickHouse is down, reception continues onto a local disk spool (WAL). Anything dropped beyond that is always counted in self-metrics — nothing is discarded silently. Under storm conditions, derived processing such as MIB resolution is deferred in a degraded mode
  • Self-monitoring: reception rate, queue depth, drop counts, unrouted ratio, store write latency, webhook delivery failures, and time of last trap received are exposed on a standard metrics endpoint (Prometheus format). Silence of sekisho itself is detected by an external watchdog via heartbeat
  • Load target: sustain 500 traps/sec with zero drops. Storms of 10× that (5,000 traps/sec) are absorbed as short bursts by the bounded queues and the spool. This envelope is comfortably achievable in a single Go process, which is also the basis for the single-instance assumption below
  • Availability non-goal: v1 assumes a single instance; HA is explicitly a non-goal. Future horizontal scaling has a natural sharding axis in a device_id hash, since state keys include the device
  • INFORMs (acknowledged notifications) are not supported. Resilience against UDP loss is provided by the combination of expiry policies (§5.3), the future ping liveness source, and the self-monitoring of this section
