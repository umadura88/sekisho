1目的と前提

本書は sekisho の実装第 1 フェーズの作業指示書である。設計の正は HLD と LLD にあり、本書と矛盾した場合は HLD / LLD が優先する(矛盾を見つけたら実装を止めて報告すること)。

最初に作るのは sekisho 本体ではなく、Trap エミュレータ trapgen である。 理由は 3 つある。①実環境(既存監視サーバ)で tcpdump により採取した本物の Trap を 開発環境で何度でも再生できるようになる。②pcap の解釈と Trap の送出には SNMP の BER エンコード/デコードの実装が必要であり、これは M1 受信機の中核(internal/snmpcodec)と 共通のコードになる — M0 は回り道ではなくコーデックのブートストラップである。③gen --out が 生成する合成 fixture は公開テストコーパス(LLD §14)になり、以降の全マイルストーンの回帰テスト 基盤になる。

機密ルール(厳守) 実環境で採取した生の pcap には実在の装置 IP・コミュニティ文字列・機器名・ベンダ識別子が含まれる。 生 pcap は、いかなる加工を経てもリポジトリに入れない(ローカルでの replay 専用)。 .gitignore に *.pcap を含め、tests/fixtures/ 配下に置けるのは trapgen gen --out が生成した合成 fixture(*.fixture.pcap)だけである。 ドキュメント・コード・コミットメッセージに装置ベンダの実名を書かない。

3M0a: pcap リプレイ(trapgen replay)

3.1配置とコマンド仕様

3.2実装要件

  • pcap の読み取りは github.com/gopacket/gopacket の pcapgo を使う (pure Go。cgo・libpcap に依存しないこと。pcapng も pcapgo.NgReader で受ける)
  • 抽出条件は「UDP かつ宛先ポート 162」。それ以外は黙ってスキップし、--dry-run と 終了時サマリで件数を報告する(total / matched / sent / errors)
  • 送出は UDP ペイロード(SNMP メッセージのバイト列)を無加工のまま net.UDPConn で送る。M0a では BER の解釈はしない
  • レート制御は token bucket(--rate)または元タイムスタンプ差の再現(--timing)。 実効レートの測定値を終了時に表示する
  • この時点で .gitignore(*.pcap を含む)、Makefile、CI(§7)も整備する

3.3テストと DoD

  • テスト用 pcap はテスト内で pcapgo.Writer により合成する(数パケットの UDP/162 + 非対象パケット混在)。リポジトリにバイナリ fixtures を置くのは M0b 以降
  • DoD: ①合成 pcap を localhost の UDP リスナ(テスト内)へ再生し、送出バイト列が元ペイロードと 一致する。②--rate 100 で 1,000 パケットを送り、所要時間が 10 秒 ±5%。③非対象パケットが 送出されない。④--dry-run がネットワークに何も出さない

4M0b: BER コーデック(サニタイザは廃止)

決定の記録(2026-07-26) 当初 M0b に含めていたキャプチャ匿名化ツール(trapgen sanitize)は、実装・検証を終えた後に 廃止した。理由: Trap の enterprise OID(1.3.6.1.4.1.<vendor>)は IANA の公開レジストリで逆引きできるベンダ識別子であり、IP を置換しても残る。かといって OID を 書き換えれば「どの Trap か」という意味そのものが壊れるため、意味を保ったままの匿名化は 原理的に成立しない。中途半端なサニタイザは「通したから安全」という誤認を生み、公開事故を 誘発するため、存在しない方が安全である。公開 fixture の供給は trapgen gen --out(§5)に よる合成に一本化し、実キャプチャはローカルの replay 専用とする(§1)。

4.1internal/snmpcodec(存続する成果物)

  • SNMPv1 / v2c メッセージの BER デコード・エンコード(メッセージ構造・PDU・varbind リスト・基本型)。 外部 SNMP ライブラリに依存せず自前実装とする — このパッケージが M1 受信機の中核になるため、 依存を持ち込まない
  • 往復契約: decode(encode(m)) == m が常に成り立ち、デコード済みメッセージの 再エンコードは羃等である。エンコードは常に正規形(最小長・確定長)とする

4.2テストと DoD

  • DoD: ①全 PDU 種別・全値型・整数境界値での往復一致テストが通る。②HLD §1.1.1 の linkDown 例を golden テストとして再現できる。③壊れた入力(切り詰め・非 SEQUENCE)をエラーとして拒否する
  • 既知の制限: 標準ライブラリ encoding/asn1 に依拠するため、不定長(indefinite length) BER はデコードできない。実運用の装置実装ではまれだが、M1 受信機の既知制限として引き継ぐ

5M0c: 合成生成器(trapgen gen)

5.1コマンド仕様とシナリオ YAML

5.2実装要件と DoD

  • Trap の組み立ては M0b の snmpcodec エンコーダを使う。sysUpTime・snmpTrapOID を 先頭 2 varbind に置く正しい v2c Trap を生成する(HLD §1.1.1 の構造)
  • --seed で全乱数を決定化できること(同じシナリオ + seed = 同じイベント列。 後の回帰テスト・負荷試験の再現性のため)
  • --pps N はシナリオの時間軸を無視した負荷モード(イベントを丸めて毎秒 N 発)
  • --out <file.pcap> は送出の代わりに合成 fixture を書き出す(--target と排他)。 タイムスタンプは固定エポック + 仮想時刻で決まり、同じ(シナリオ, seed, duration)の出力は バイト単位で再現される。シナリオ終了時には保留中の linkUp をフラッシュし、 全 linkDown に対応する linkUp が必ず含まれる。これが公開 fixture(§1)の唯一の供給経路である
  • DoD: ①シナリオの linkdown_up が down → up の順で対で生成される。②loopback で --pps 5000 を 5 分間維持し、送出実測が ±5% 以内(LLD §14 の負荷テストの土台)。 ③生成物を snmpcodec でデコードした golden JSON テストが通る

6M1 以降の接続

M0 完了時点で、①BER コーデック(internal/snmpcodec)、②再現可能なテスト入力 (gen --out の合成 fixtures + gen シナリオ)、③負荷試験器、の 3 点が揃う。M1(受信機 → MIB 解決 → ClickHouse 格納、unrouted 一覧 CLI)は LLD §10 のパイプラインの左半分を snmpcodec の上に 実装する。M1 の詳細ブリーフは M0 完了後に本書を更新して追記する(現段階では着手しないこと)。

7開発環境と CI

  • Go 1.23 以上。モジュール名は github.com/umadura88/sekisho
  • Makefile: make build(全バイナリ)/ make test(go test -race ./...)/ make lint(golangci-lint run)
  • CI(.github/workflows/ci.yml を新設): push / PR で build・test(-race)・lint を実行。 既存の pages.yml(site/** のみ発火)には触れない
  • 依存は最小に保つ。現時点で許可されている外部依存: gopacket(pcap I/O と パケット再構成)、YAML パーサ、テストアサーション。SNMP ライブラリは追加しない (snmpcodec は自前実装。§4.2 の理由)

8実装エージェントへの指示

  1. 着手前に HLD と LLD を通読すること。用語 (Event / Alarm / device_id / mib_set 等)は両文書の定義に従う
  2. 作業はフィーチャーブランチ(例: m0a-replay)で行い、PR で main に入れる。 main への直接 push はしない
  3. コミットは小さく分け、全コミットに DCO の sign-off を付ける(git commit -s)
  4. site/ 配下(設計ドキュメント)は変更しない。設計との矛盾や不明点を見つけたら、 実装で勝手に解決せず PR 説明または issue に書いて止める
  5. テストを先に書く(特に snmpcodec は往復一致・golden テストが仕様そのもの)。 make test lint が通らない状態でコミットしない
  6. §1 の機密ルールを厳守する。生 pcap・実装置の識別子・ベンダ実名をリポジトリに入れない
  7. 各マイルストーンの終わりに、DoD(§9)に対する自己チェック結果を PR 説明に含める
