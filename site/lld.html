1本書の位置づけ

本書は HLD で確定したアーキテクチャの実装仕様である。HLD が LLD 送りとした 未決事項 — ルーティング DSL の正式スキーマ、alarm.* ストリームのスキーマ詳細、順序逆転の猶予窓、 保持期間の終端、MIB の配置規約、公開契約の詳細 — をここで確定する。本書内で「提案」と明記した数値は 実装初期のデフォルトであり、実測に基づいて変更してよい(変更は設定で吸収する)。

3ルーティング DSL 正式仕様

3.1routes.yaml

  • trap_oid のパターンは完全一致か末尾 .* の prefix 一致のみ。 正規表現・中間ワイルドカードは意図的に許可しない(全順序の単純さを守る)。IF-MIB::linkDown の 形式のシンボル表記も受け付け、ロード時に数値 OID へ解決する
  • where は varbind 名(または生 OID)→ 条件のマップ。条件は「値」「値のリスト(OR)」 「{ gte: N } / { lte: N }(数値型のみ)」の 3 形式。列挙はラベルで書き、 ロード時に型付き値へコンパイルする
  • action は stateful: <rule名> / drop / bucket: unrouted の 3 種。 default ブロックはネスト 1 段のみ許す

3.2rule ファイル

表 1rule フィールド定義
フィールド型必須意味
rulestring(kebab-case)必須ルール ID。リポジトリ内で一意

keyテンプレート必須状態キー。{source} = 解決済み device_id、{<varbind名>} = 値、{instance_of(<名>)} = 添字

severity の列挙は critical / major / minor / warning / info の 5 段とする(X.733 準拠。cleared は severity ではなく状態遷移)。

4状態エンジン仕様

4.1Alarm 状態機械

表 3状態遷移表(行 = 現在状態、列 = 入力)
状態 \ 入力raise イベントclear イベントexpire手動 clearflap 閾値超過calm 経過
(なし)raised を生成 / alarm.raised記録のみ(遷移なし)————
raisedcount++、遷移なしcleared / alarm.cleared(trap)cleared / alarm.cleared(expired)cleared / alarm.cleared(manual)flapping フラグ ON / alarm.flapping—
raised + flappingcount++、遷移は記録内部状態は追従、フラグ維持同上同上—フラグ OFF / alarm.updated
  • cleared は終端状態。同一キーの次の raise は新しい alarm_id を生成する(再発は別 Alarm。 関連づけは key で追える)
  • severity の変化(パターン B の severity_from)は raised のまま alarm.updated を発火する

4.2順序逆転の猶予窓(grace)

処理は device_id ハッシュでシャーディングされたワーカー(§10)がキー単位に直列実行する。各キーは 直近イベントを grace(既定 2 秒、rule で上書き可)だけ保留し、保留中に received_at が より古いイベントが届いた場合は received_at 順に並べ替えてから状態機械に投入する。grace を過ぎた 遅延イベントは「遅延到着」として Event 層に記録し、状態遷移には使わない(バックテストでは正順で 評価されるため、ライブとリプレイの差はこの窓の内側に限定される)。

4.3expire スケジューラ

expire_after を持つ Alarm は raise 時に expires_at を書き込む。スケジューラは 60 秒周期で expires_at <= now() を走査し(部分インデックス、§5.1)、reason=expired の clear 遷移を通常の遷移と同じ経路(outbox 含む)で実行する。

5データベーススキーマ

5.1PostgreSQL

Alarm 遷移と outbox 挿入は同一トランザクションで行う(HLD §6 の transactional outbox)。 alarms_active_key の部分ユニーク制約が「同一キーに raised は高々 1 つ」をデータベースレベルで保証する。

5.2ClickHouse

ingress_events は HLD 図 12 のとおり。加えて 2 つの Materialized View を持つ。

保持期間(提案): ホット層(ローカルディスク)90 日 → S3 層へ移動、総保持 390 日(13 ヶ月。 年次比較 + 余裕)。バックテストの対象は全階層とし、S3 層に及ぶ場合は速度低下を許容する (進捗を API で返す)。

9MIB 配置規約とロード仕様

  • 同梱(mibs/std/): SNMPv2-SMI / SNMPv2-TC / SNMPv2-MIB / IF-MIB / SNMP-COMMUNITY-MIB(snmpTrapAddress 用)等、IETF 由来の標準 MIB のみ。private MIB は 再配布不可のため同梱しない
  • ユーザ持ち込み: ルールリポジトリの mibs/(推奨)またはローカルの mib_paths 設定ディレクトリ。ロード順は std → ユーザの順で、同名モジュールはユーザ側が勝つ
  • mib_set: ロードした全モジュールの正規化ハッシュ(SHA-256 先頭 12 桁)。 Event に刻印され(HLD 図 12)、バックテストの決定性の基準になる。過去の mib_set は mib_snapshots ディレクトリに保存し、リプレイ時に参照する
  • 未解決の扱い: 解決できない OID は生のまま通す(HLD §5.1 の縮退動作)。未解決率は メトリクスで公開する

10受信パイプライン実装

  • ディスクスプール(WAL): ClickHouse 停止時、CH batcher は 64MB 単位のセグメント ファイルに追記する(fsync 1 秒間隔)。復旧後は event_id の冪等挿入で再送する。起動時は必ずスプールの リプレイから始める
  • 縮退モード: frame channel の使用率が 80% を超えたら MIB 解決を後回しにし (生 OID のまま格納し、後段のバックフィルで解決)、デコードとルーティングを優先する
  • HLD §12 の目標負荷(定常 500 traps/sec、バースト 5,000)に対し、この構成の律速は CH 挿入では なく PG トランザクションだが、遷移を伴う Trap は全体の一部であり、shard 並列で十分に収まる

13バックテスト実装

  • 入力: ルール YAML(単体または差分セット)、期間、対象 device の絞り込み(任意)
  • 実行: ClickHouse から received_at 昇順でイベントを読み、隔離した状態エンジン インスタンスでリプレイする。ライブの Alarm 状態には一切影響しない
  • 決定性: 評価は (イベント列, ルール, mib_set) の純関数(HLD §8)。イベントに刻印された mib_set の スナップショットで raw_value を再解決する
  • 出力: { matches, alarms_raised, alarms_cleared, mean_duration, flap_count, top_keys[], sample_lineage[] }。CI はこれを PR コメントに整形する
  • ジョブ管理: POST /backtest は 202 + job ID を返し、進捗(走査済み日数)をポーリングで返す

14テスト戦略

  • 公開フィクスチャ: tests/fixtures/ に pcap(生 UDP フレーム)と golden JSON(期待される分解済みイベント・Alarm 遷移列)を対で置く。実装置がなくても受信 → 遷移の 全経路を回帰テストできる(M1 成果物)
  • 決定性テスト: 同一 fixtures を 2 回リプレイし、Alarm 遷移列が完全一致することを CI で常時検証する
  • DSL golden テスト: ルール + イベント列 → 期待遷移列、を YAML で記述するテーブル駆動形式
  • 負荷テスト: 合成 Trap 生成器で 5,000 traps/sec × 5 分を流し、drop 0・スプール回復を検証する

1Purpose of This Document

This document is the implementation specification of the architecture fixed in the HLD. It settles the items the HLD deferred: the formal routing DSL schema, alarm.* stream details, the out-of-order grace window, the end of the retention period, MIB conventions, and the details of the public contracts. Values marked as "proposed" are initial defaults; they may be revised based on measurement (changes are absorbed by configuration).

2.1The sekisho repository (this one)

2.2The rules repository (scaffolded by sekisho rules init)

3Routing DSL Specification

3.1routes.yaml

  • trap_oid patterns are exact or trailing-.* prefix only. Regular expressions and mid-pattern wildcards are deliberately not allowed (preserving the simplicity of the total order). Symbolic notation (IF-MIB::linkDown) is accepted and resolved to numeric OIDs at load time
  • where maps varbind names (or raw OIDs) to conditions. Three condition forms: a value, a list of values (OR), and { gte: N } / { lte: N } (numeric types only). Enums are written as labels and compiled to typed values at load time
  • action is one of stateful: <rule> / drop / bucket: unrouted. The default block allows one level of nesting

4State Engine Specification

4.1The alarm state machine

Table 3Transition table (rows = current state, columns = input)

  • cleared is terminal. The next raise on the same key creates a new alarm_id (recurrence is a new alarm; correlation is traceable via the key)
  • Severity changes (pattern B's severity_from) fire alarm.updated while staying raised

4.2The out-of-order grace window

Processing is serialized per key by shard workers hashed on device_id (§10). Each key holds its most recent event for grace (default 2 seconds, overridable per rule); if an event with an older received_at arrives during the hold, events are reordered by received_at before entering the state machine. Late events beyond the grace window are recorded in the event layer as late arrivals and do not drive transitions (backtests evaluate in true order, so live/replay divergence is bounded by this window).

4.3The expire scheduler

Alarms with expire_after get expires_at written at raise time. A scheduler scans expires_at <= now() every 60 seconds (partial index, §5.1) and executes the reason=expired clear transition through the normal path, outbox included.

5Database Schemas

5.1PostgreSQL

Alarm transitions and outbox inserts run in one transaction (the transactional outbox of HLD §6). The partial unique index alarms_active_key enforces "at most one raised alarm per key" at the database level.

5.2ClickHouse

ingress_events is as in HLD Figure 12, plus two materialized views.

Retention (proposed): hot tier (local disk) 90 days, then the S3 tier; total retention 390 days (13 months — year-over-year comparison plus margin). Backtests cover all tiers; slower scans over the S3 tier are accepted (progress is reported via the API).

9MIB Conventions and Loading

  • Bundled (mibs/std/): IETF standard MIBs only — SNMPv2-SMI / SNMPv2-TC / SNMPv2-MIB / IF-MIB / SNMP-COMMUNITY-MIB (for snmpTrapAddress) and the like. Private MIBs are not redistributable and are never bundled
  • User-supplied: the rules repository's mibs/ directory (recommended) or local mib_paths directories. Load order is std → user; a same-named module from the user side wins
  • mib_set: a normalized hash of all loaded modules (first 12 hex chars of SHA-256), stamped on every event (HLD Figure 12) as the basis of backtest determinism. Past mib_sets are kept in a mib_snapshots directory for replay
  • Unresolved symbols: unresolvable OIDs pass through raw (the graceful degradation of HLD §5.1). The unresolved ratio is exposed as a metric

10Reception Pipeline

  • Disk spool (WAL): while ClickHouse is down, the CH batcher appends to 64MB segment files (fsync every second). On recovery, events are re-sent via idempotent event_id inserts. Startup always begins by replaying the spool
  • Degraded mode: when the frame channel exceeds 80% utilization, MIB resolution is deferred (events are stored with raw OIDs and backfilled later), prioritizing decode and routing
  • Against the HLD §12 load target (sustained 500 traps/sec, bursts of 5,000), the bottleneck of this structure is the PG transaction, not CH inserts — but only a fraction of traps drive transitions, and shard parallelism covers it comfortably

13Backtest Implementation

  • Input: rule YAML (single or a diff set), a period, and an optional device filter
  • Execution: events are read from ClickHouse in received_at order and replayed through an isolated state-engine instance; live alarm state is never touched
  • Determinism: evaluation is a pure function of (event stream, rules, mib_set) (HLD §8); raw_value is re-resolved against the mib_set snapshot stamped on each event
  • Output: { matches, alarms_raised, alarms_cleared, mean_duration, flap_count, top_keys[], sample_lineage[] }. CI formats this into the PR comment
  • Job management: POST /backtest returns 202 + a job ID; progress (days scanned) is available by polling

14Test Strategy

  • Public fixtures: tests/fixtures/ pairs pcaps (raw UDP frames) with golden JSON (expected decomposed events and alarm transition sequences). The full reception-to-transition path is regression-testable without real devices (an M1 deliverable)
  • Determinism tests: the same fixtures are replayed twice and the alarm transition sequences must match exactly, verified continuously in CI
  • DSL golden tests: table-driven YAML of rule + event sequence → expected transitions
  • Load tests: a synthetic trap generator drives 5,000 traps/sec for 5 minutes, verifying zero drops and spool recovery
